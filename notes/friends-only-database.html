Design note · 9 October 2026

A database you share only with your friends

Why the password in a serverless user database is its weakest point, why the usual server-side fixes do not carry over, and the design that fixes it along with the next billion users.

Where this starts. bep46-webrtc publishes web pages and runs small apps with no server: the people who have a page open are the computers serving it. They find each other through a WebTorrent tracker and talk over WebRTC. One of its example apps, the Swarm Registry, is a user database with the same property. Every account is an Ed25519 keypair. The secret key is encrypted under the account's password and published inside a signed record that every peer replicates, which is what lets you sign in from any browser with nothing but a username and a password. Catwalk, a 2004-style social network for cats, is built on top of that. The accounts README says plainly that the sealed key can be attacked offline.

This note started from a fair question about that design. The key derivation runs scrypt at a cost of 215, which sounds low, so could the passwords be 2256 and elliptic instead? It ends somewhere larger.

What the 215 actually is

The short version: the account key is already a 256-bit elliptic-curve key. The 215 is a different kind of number, it is the price of one password guess, and making that number bigger has a hard ceiling. What decides the security is the password's entropy. That can be pushed to 256 bits, but then it stops being something a human remembers.

Each account is an Ed25519 keypair, plus an X25519 key for Catwalk's friends-only posts, so the identity itself is "elliptic and 2256" today. The password never signs anything. It only unlocks a copy of that key: the key is encrypted with XSalsa20-Poly1305 under a 256-bit key that scrypt derives from the password and a random 16-byte salt, and that encrypted box is published in the signed record for everyone to replicate. The 215 is scrypt's cost parameter N. It says one guess must touch 32 MiB of memory and burn a measurable amount of time. It is a work factor, not a key length or a password space.

Because the box is public, there is nothing to rate-limit. Anyone can download it and guess as fast as their hardware allows. So the attacker's total cost is simply the number of guesses times the cost per guess. Here is the cost per guess, measured on the project's tracker host, which has slow cores, so a current laptop is several times faster, both native and in the same pure-JS library the browser runs:

Why raising N is not the lever

Going from 215 to 217 makes every guess four times dearer, which is worth two bits of password. It also makes every login four times slower, and 220 means a gigabyte of RAM per sign-in, which phones cannot do. The attacker and the user pay the same per-guess price, so N is capped by the user's patience at maybe two or three bits of gain. Password entropy has no cap: each extra word is 12 bits for free. Raising N modestly to 216 or 217 is still reasonable, and records carry their own parameters so old accounts keep working, but it is a tweak, not a fix.

One consequence worth knowing: changing the password re-seals the same key under the new password. A peer that kept the old record can still crack the old weak password and get the current key. The only escape from a weak password is a new account.

How to get to "2256 and elliptic"

The secret has to come from the device rather than from memory. Four routes, cheapest first:

  • Refuse weak passwords and generate strong ones. Keep username plus password, add an entropy estimate at registration with a floor around 60 bits, and a "generate a passphrase for me" button producing six diceware words for a password manager. No protocol change, and it takes most accounts from "days" to "never".
  • Key login, no box at all. Let a user register with just a key, like the page publisher's .key file, shown as a 24-word mnemonic or a file. Nothing is published to attack. This needs a small record-format bump, since the validator currently requires a box on every live account. The user carries the key instead of remembering it.
  • Passkeys with the PRF extension. The browser's authenticator (Touch ID, Windows Hello, a security key) derives a 256-bit secret per site and the account key is wrapped under that. Sign in with a fingerprint, nothing guessable in the swarm. It works on this site, but not inside the page publisher's sandboxed iframe, where there is no origin, and browser support is still uneven.
  • Argon2id instead of pure-JS scrypt. A WebAssembly build is several times faster on the user's side, so you can afford more memory per guess at the same login time. Incremental, same category as raising N.

What cannot be done serverless: a secret pepper, OPAQUE-style password exchange, or lockouts, since all of those need something the attacker does not have, held somewhere other than the user's device. The first route is cheap and worth doing regardless. The rest of this note is about where the others lead.

The pepper, and why it turns into a device secret

A natural suggestion at this point is the pepper that PHP applications use: a long random string kept in the application's config and prepended to every password before hashing, so that a user whose password is "password" is still safe, and never has to remember the long part. The intuition about what it buys is right. But it only works because of where the secret lives, and in a serverless system that forces a specific design.

How the trick works. The app has a long random string in its config file. Before hashing, the password gets combined with it, for example afoa8f7asdofgadf87_password goes into bcrypt, or the password goes through HMAC with the pepper as the key. The user never knows the pepper. The point is separation: the hashes sit in the database, the pepper sits in a file on the web server. The common breach is a database dump through SQL injection or a stolen backup, and that dump is useless without the pepper, because now every guess has 256 unknown bits in it. If the attacker gets the whole server, config included, the pepper is gone and you are back to bcrypt and password strength.

Why it does not transfer directly. The trick needs a place the attacker cannot read. Here the "database" is public by design, every peer holds it. So where would the pepper go?

  • In the page's code: then everyone has it, including the attacker, and it adds nothing.
  • On a server: then the server has to hand it out to whoever logs in, so either it gives it to the attacker too, or it rate-limits and becomes the one thing that must be online for anyone to sign in. That is the design the whole project exists to avoid.
  • On the user's device: this is the only place that is private, and it is the version that works.

What it becomes here: a device secret. At registration the browser generates 256 random bits, stores them in the browser's storage, and seals the account key under scrypt of the device secret plus the password. The published box now needs both. Offline guessing against the swarm is dead regardless of password, because the guess space includes 256 unknown bits. The password still matters in one case only: someone who gets hold of the device secret, a stolen laptop or a leaked backup, has to guess the password to use it. So "password" as a password becomes "fine against the internet, weak against whoever has your device". That is a huge improvement over today, and it is an honest statement of what the trick gives.

The costs are all about carrying it:

  • Signing in from a new browser needs the secret moved there once, as a QR code, a file, or 24 words. Password-only login from any browser, which is the registry's current headline, goes away for these accounts. The browser can hold it forever after that.
  • Lose every device that has it and the account is gone, same as losing a password, but a new way to lose. Registration has to insist on a backup copy.
  • A page published through the bep46 publisher runs in a sandboxed iframe with no persistent storage, so there the secret cannot be remembered and would have to be pasted each time. On this site and on the tracker host it works fine.
  • If the user keeps the secret in a password manager, that is identical to generating a strong password and keeping that in the manager. The pepper is just a strong password the user never types. The genuinely new capability is the browser remembering it.

A practical shape would be an option per account: "portable", password only with a strength floor, or "device-locked", device secret plus any password with a mandatory backup step. The record format already carries the key-derivation parameters, so this is a flag in that block, and existing accounts keep working. The attacker's view of a device-locked account is the same as the key-login route above, 2256, so this is a way to get there while keeping a login form that feels like a login form.

A database you share only with your friends

The question that reframes all of this: what if the database were only ever shared with your friends? That would also address a second problem that global replication has. At a billion users, nobody wants, and no browser could hold, a single database of absolutely everything.

This is the design the serious peer-to-peer social projects ended up with. Secure Scuttlebutt arrived at it in 2014: every person has their own signed feed, and you replicate only the feeds of your friends, optionally friends of friends. Briar does the same between contacts, and Earthstar and the newer Willow protocol are built around small shared spaces rather than one global set. So the instinct is well tested. Here is what it means for this codebase, what it fixes, what it does not, and where the hard parts are.

What changes in the data model

Today there are two global maps, the account directory and Catwalk's social ledger, and every open tab replicates all of both. In a friends-only design the unit of replication becomes the author. All of my records, my account record, profile, posts, friendships and pokes, form my feed, signed by my key, and you hold my feed only if we are friends. The nice thing is that this project already has the primitive: a feed is exactly a BEP-46 mutable page whose address is my public key. Catwalk becomes a browser that visits its friends' addresses and merges what it finds. The replica code barely changes, it gains a filter, "accept records whose owner is in my friend set", and the swarm per user already exists.

The real shift is that the database becomes subjective. There is no longer a single answer to "who is alice". There is the alice my friends know, and the name I choose to show for a key, a petname. Zooko's triangle says names can be global, secure or human-friendly, pick two. The current registry picked global and human-friendly and lives with duplicate claimants. The friends design picks secure and human-friendly. If global search by name still matters, it can be an opt-in phone book, sharded by a hash prefix of the name so a lookup joins one small swarm instead of loading everything.

What it does for the password problem

Less than it looks, unless you take it one step further. Partitioning shrinks the audience for your sealed key from the whole internet to your friends and their friends. That is real: a stranger cannot even obtain the box to attack it. But the people who hold it are now exactly the ones who can socially engineer you, and in a 2004 Facebook parody, accepting a friend request would mean handing that person a copy of your sealed key. One compromised friend's browser is enough. So this is a reduction of exposure, not a cryptographic fix.

The step that makes it a fix: stop putting a crackable box in the swarm at all. Keep the key on your own devices, sealed under your password for local protection, and give your friends Shamir shares of it, say any three of five. No single friend holds anything attackable. Signing in from a new device, or after losing everything, means asking three friends, who confirm out of band that it is really you. That human decision is the rate limiter no server could provide, and it is what finally makes a weak password acceptable, because the weak password only guards a device the attacker would also need to steal. This is the social recovery scheme that crypto wallets converged on, and a friends-only database is the natural home for it.

What it does for scale

This is where the idea is clearly right. Global replication of a billion accounts cannot fit in a browser at any record size. Friends-only replication scales with your neighbourhood instead:

what one person replicatesfeedsrough storage
friends only, full feeds~150tens of MB
friends of friends, full feeds~20,000gigabytes, too much
friends in full, friends of friends as profile cards only~20,000 cardsmanageable

Scuttlebutt learned the middle row the hard way and moved to partial replication, so the sensible dial is one hop in full and two hops as cards. The tracker stays the one global component, but it only does signalling and never sees content, and its load is a few kilobytes per connection regardless of how big the social graph gets. Partitioning also fixes the metadata leak the README lists today: strangers no longer see your friendships, posting times or ciphertexts, and nobody anywhere holds a copy of everything, which matters for privacy and for not being a honeypot.

The hard parts, honestly

  • Availability. Your feed is reachable only while you or a friend has a tab open. Native Scuttlebutt apps run all day. Browsers do not, and with ten friends the expected number online is often zero. Scuttlebutt's answer was pubs, always-on peers that follow you, which is a server again, though anyone can run one and it holds only what it is already allowed to see. An optional always-on peer, perhaps even a Node process on the tracker host that stores encrypted feeds, is probably unavoidable for a usable product.
  • Discovery and first contact. With no global map, a stranger's friend request has nowhere to land, because I only replicate people I already chose. Invite links carrying a public key solve friend-making, and a per-user inbox swarm solves requests from strangers, at the price of a spam channel that needs a cost or an invite to post into.
  • Unfriending cannot unsend. A removed friend keeps what they replicated. The per-author key epochs Catwalk already uses handle future posts, which is the best anyone can do.
  • Hosting your friends. Each person stores and serves their friends' content, which is easier to accept than serving strangers, but it is still their content on your disk.

Open decisions

Four decisions would shape a design:

  1. One hop or two, in full or as cards.
  2. Whether global username search must survive, or invite links are enough.
  3. Whether an optional always-on peer is acceptable, given the project's serverless promise.
  4. Whether the account's key should leave the user's devices at all, or only as shares.

Nothing in this note is implemented. The code it describes is in accounts/ and catwalk/ in the repository, and the landing page explains the project from the start. Comments, corrections and better ideas: open an issue.
