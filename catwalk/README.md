# Catwalk — a 2004 social network with no server

**Live:** <https://mrmartin.net/bep46-webrtc/catwalk/> (GitHub Pages; also <https://bot.martintech.co.uk/catwalk/>) · demo accounts `mittens`, `whiskers`, `tom`, `luna`, `oliver`, `cleo`, `simba`, `nala`, `felix`, `pixel`, password `catnip2004`

A parody of a certain early social network, rebuilt on the [accounts layer](../accounts/) one directory up: register, make a profile with a little SVG cat, find other cats, send and confirm friend requests, poke, and post — to everyone, or to your friends only. There is no server behind any of it. Every account, friendship and post is a signed record that lives in whoever has the page open; browsers find each other through a WebTorrent tracker and talk over WebRTC. Friends-only posts are encrypted, so a peer that relays them cannot read them.

The page ships with a sample network — ten cats, their friendships, thirty posts and some pokes — as genuinely signed records, ingested at start-up exactly as if they had arrived from a peer. So the first visitor sees a populated site, and from that moment on is also one of the browsers serving it.

```bash
cd catwalk && npm install
npm test          # 13 tests: records, privacy, replication over a simulated swarm, the sample data
npm run build     # dist/index.html — one self-contained file, zero external requests
npm start         # dev server: http://127.0.0.1:8081/catwalk/web/?tracker=ws://127.0.0.1:8000
```

(`npm run tracker` in `../accounts` gives you the local `ws://127.0.0.1:8000` tracker for development. Against the internet the page uses the project's own `wss://bot.martintech.co.uk`.)

## What is reused and what is new

From `../accounts/src/`: accounts (ed25519 key sealed under scrypt(password)), the convergent replicated map, the gossip protocol (`Replica`), the WebTorrent channel-swarm transport, and the crypto wiring. Catwalk adds:

| file | what |
|---|---|
| `src/social.js` | The social record format and its strict validator: `profile`, `friend`, `post`, `poke`, `fkey`. |
| `src/ledger.js` | A second replicated map keyed by record id (an owner has many records), same merge rule as the account directory. The shared `Replica` drives it with `keyField: 'id'`. |
| `src/privacy.js` | Friends-only posts: box keys derived from the account key, a per-author *friends key* sealed to each friend, epochs and a key chain. |
| `src/catwalk.js` | The application: profiles, friend requests, posts, pokes, feeds, and who may read what. |
| `src/avatar.js` | The cat face, as inline SVG from fur, eye colour and a bit of the key. |
| `web/` | The page. `seed.js` is the sample network, generated by `tools/seed.js`. |

Two swarms are joined: `sha1("catwalk/accounts/v1")` for account records and `sha1("catwalk/social/v1")` for everything else — separate from the Swarm Registry's directory so the demo cats do not show up there.

## The records

Every social record is signed by the account key of its `owner`, and its `id` starts with `<kind>:<owner>`, so nobody can publish a profile, friend link or post in somebody else's name whatever key they sign with. Per id, the highest `seq` wins; deletions are tombstones that stay.

```
profile:<pk>              { name, tagline, about, fur, eyes, box }
friend:<pk>:<other>       { to }       a friendship is two of these, one each way; one alone is a pending request
poke:<pk>:<other>         { to }       re-poking bumps seq; ts is the latest poke
post:<pk>:<16 hex>        { aud:"public", text } | { aud:"friends", epoch, nonce, ct }
fkey:<pk>                 { epoch, keys:{ <pk>: sealed friends key }, chain:[ older keys, each under the next ] }
```

## Friends-only, without a server to enforce it

Everyone relays everything, so "friends only" has to mean encryption:

- Each account derives an x25519 keypair from its account secret (nothing extra to store) and publishes the public half in its profile (`box`).
- Each author keeps a random 32-byte *friends key*. The current one is sealed to every friend's box key (and to the author) in the author's `fkey` record; friends-only posts are `secretbox(text)` under it, tagged with the key's `epoch`.
- Sending a friend request seals your key to them straight away (you chose them); confirming one seals yours to the requester. If they had no profile yet, `reconcile()` catches up the next time you are signed in and their profile arrives.
- Removing a friend starts a new epoch: a fresh key, sealed only to the friends who remain, with the previous key wrapped under the new one in `chain`. Since the new `fkey` record replaces the old one, the removed friend has no key at all from then on — bar whatever they cached while they had it; nothing can be un-sent. A new friend receives the current key and can unwind the chain to read your older posts too.
- Changing your password re-seals the same account key, so nothing here changes.

What it does not do: hide *that* you posted (record metadata — who, when, how long — is public), hide your friend list, or protect against a friend copying your post. The accounts layer's caveats (offline password guessing, username squatting, durability only while someone holds the records) apply unchanged — read [its README](../accounts/README.md#what-this-does-not-protect-against--read-before-relying-on-it).

## Tests

`npm test` runs, in Node with a simulated swarm:

- **social** — every kind of record a cat publishes validates and every single-field tamper breaks it; a record with someone else's id is rejected even with a valid signature; tombstones for other people's posts are rejected; merge rules.
- **privacy** — friends read, strangers and signed-out visitors do not; a pending request is not friendship; unfriending closes everything to the ex-friend while a new friend reads the whole history through the chain; `reconcile()` after a late profile; the box key survives a password change; pokes.
- **replication** — three peers: profiles, a friend request and its confirmation, public and friends-only posts crossing the swarm; a late joiner receiving the whole ledger and signing in on it; a hostile peer that forges, replays and spams.
- **seed** — the shipped sample data verifies record by record, loads into an empty node like gossip, every demo cat signs in with the demo password, and friends can read each other's friends-only posts.

`npm run smoke` (after `npm run build`) drives the **built page** in jsdom without a browser: the home page with sample posts, the members list, a profile, signing in as a demo cat, reading a friends-only post, posting, sending a friend request, poking, editing the profile, logging out (the friends-only post disappears) and persistence to `localStorage`. The real-browser layer of `../accounts` (two Chromiums over WebRTC) is the model for going further; it is not wired up for Catwalk yet.

## Deploying

`npm run build` produces `dist/index.html`. It is hosted by the project's tracker at <https://bot.martintech.co.uk/catwalk>, and because it is one self-contained file it can also be published *into* the swarm with the [BEP-46 page publisher](../README.md): open the publisher, **Create new content**, pick `dist/index.html`, and Catwalk gets a `bep46:` address served by its own visitors.

To regenerate the sample network with fresh identities: `npm run seed` (then rebuild). The demo password is in `tools/seed.js`.
